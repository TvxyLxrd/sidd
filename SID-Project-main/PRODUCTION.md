# Публикация SID

Порядок действий для развёртывания на боевом сервере. Пункты идут в том порядке, в котором их нужно выполнять.

---

## 1. База данных

Режим `memory` для боевой среды не годится: данные живут до перезапуска процесса. Нужен PostgreSQL 15 или новее.

```bash
createdb sid_production
createuser sid_user --pwprompt
```

Дайте пользователю права только на эту базу. Учётная запись суперпользователя приложению не нужна.

## 2. Секреты

```bash
npm run generate-secrets
```

Команда выдаёт три значения: `JWT_SECRET`, `JWT_REFRESH_SECRET`, `ENCRYPTION_KEY`.

**`ENCRYPTION_KEY` нельзя менять после первой записи данных.** Телефоны и тексты заказов хранятся зашифрованными; со сменой ключа они перестанут расшифровываться. Храните резервную копию ключа отдельно от резервной копии базы — вместе они дают ровно то, от чего шифрование защищает.

## 3. Конфигурация

Возьмите за основу `backend/.env.production.example`, скопируйте в `backend/.env` и заполните.

Обязательный минимум:

| Переменная | Значение |
|---|---|
| `NODE_ENV` | `production` |
| `DB_DRIVER` | `postgres` |
| `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | доступ к базе |
| `DB_SSL` | `true`, если база на другом хосте |
| `JWT_SECRET`, `JWT_REFRESH_SECRET`, `ENCRYPTION_KEY` | из шага 2 |
| `CORS_ORIGIN` | ваш домен, без звёздочки |
| `BCRYPT_ROUNDS` | `12` |
| `REDIS_DISABLED` | `false`, если экземпляров приложения больше одного |

Сервер проверяет секреты при старте и отказывается подниматься в боевом режиме со значениями из шаблона, с ключами короче 32 символов и когда оба JWT-секрета совпадают.

## 4. Схема и справочники

```bash
npm run migrate
npm run seed
```

`migrate` создаёт семь таблиц, `seed` наполняет справочник направлений работы. Учётные записи не создаются ни там, ни там.

## 5. Администратор

```bash
npm run create-admin -- --email you@domain.ru
```

Пароль выводится один раз. Не короче 12 символов, слабые значения отклоняются.

Повторный запуск с тем же адресом меняет пароль и отзывает все сессии этого пользователя — так же сбрасывают доступ при компрометации.

## 6. Запуск

```bash
npm start
```

или под менеджером процессов из `ecosystem.config.json`:

```bash
pm2 start ecosystem.config.json --env production
```

## 7. Обратный прокси и TLS

Приложение слушает HTTP и рассчитывает, что TLS терминируется на прокси. В боевом режиме оно само перенаправляет HTTP на HTTPS и включает HSTS, поэтому прокси обязан передавать `X-Forwarded-Proto` — иначе получится цикл перенаправлений.

Пример настроек — в `nginx/nginx.conf`. Сертификат удобнее всего получить через Let's Encrypt.

## Проверка после развёртывания

```bash
curl https://your-domain.ru/api/v1/health
```

Ожидаемый ответ содержит `"status":"healthy"` и `"driver":"postgres"`. Если драйвер `memory-postgres` — конфигурация не подхватилась.

Дальше проверьте вручную:

- [ ] Открывается главная страница, работает регистрация заказчика
- [ ] Вход администратора выполняется, админ-панель открывается
- [ ] `http://` перенаправляется на `https://`
- [ ] Заголовок `Content-Security-Policy` присутствует в ответе
- [ ] Заголовок `Strict-Transport-Security` присутствует
- [ ] `/.env` и другие служебные пути отдают 404
- [ ] В базе в таблице `users` поле `phone` содержит строку вида `enc.v1....`

## Что настроить отдельно

**Резервное копирование.** Ежедневный дамп базы плюс отдельно хранимый `ENCRYPTION_KEY`. Дамп без ключа бесполезен, ключ без дампа безвреден — в этом и смысл раздельного хранения.

**Ротация журналов.** Файлы в `backend/logs/` растут без ограничений. Настройте logrotate или задайте `LOG_LEVEL=warn`.

**Мониторинг.** Эндпоинт `/api/v1/health` подходит для проверок доступности.

## Чего пока нет

Эти пункты не закрыты и требуют работы до выхода на реальных пользователей и платежи:

- Мобильное приложение не подключено к серверу — публиковать его нельзя
- Приём платежей не реализован
- Внешний тест на проникновение не проводился
- Аттестация системы по требованиям 152-ФЗ не пройдена
